# Changelog

## Unreleased

- (EN) `probe firmware exit-iap` returns a probe that sits in IAP mode to the application it already holds, without writing any firmware. IAP entry turns out to be persistent: a probe put into IAP re-enumerates as `4348:55e0` after a full power cycle even when its application is untouched, and the end frame `83 02 0000` - which needs no start and no data - is what makes the bootloader jump. So a probe that was put into IAP by mistake no longer needs a firmware image to come back. The same persistence means an interrupted update is always retryable: after killing an update 63% into the write pass and power-cycling, the probe still came up in IAP and a plain re-run of `probe firmware update` restored it (verified on a WCH-LinkE). `doctor` now points at both commands for an IAP-mode device.
- (JA) `probe firmware exit-iap` を追加: IAP mode に留まっている probe を、firmware を書かずに今入っている app で起動させる。IAP entry は不揮発だと分かった — IAP に入れた probe は、app が無傷でも電源を入れ直すと `4348:55e0` として再列挙し、jump させるのは終了 frame `83 02 0000`(開始もデータも不要)だけ。誤って IAP に入れてしまった個体を firmware image 無しで戻せる。同じ性質から中断した更新は必ず再試行できる: 書込 pass の 63% で kill して電源を入れ直しても IAP のままで、`probe firmware update` の再実行だけで復旧した(WCH-LinkE 実機で確認)。`doctor` は IAP mode の device に対して両コマンドを案内するようにした。
- (EN) `probe firmware update --image <FILE>` is implemented (was a scaffold returning exit 70): it rewrites the probe's OWN firmware over WCH's IAP path - send `81 0f 01 01`, wait for the probe to re-enumerate as `4348:55e0`, stream the image twice (write pass + verify pass) in 60-byte frames on the bulk pair `0x02`/`0x82`, end, and report the version the probe comes back with. WCH's WCH-LinkUtility (Windows-only) was the only tool that could do this - probe-rs, wlink and minichlink do not update probe firmware - so a WCH-LinkE can now be updated, downgraded, or rescued out of IAP mode from Linux/macOS. A probe already sitting in IAP mode is written directly (no entry command), so an interrupted update is recovered with the same command. The image is checked before anything is sent: a bootloader+application file (`*_APP_IAP.bin`, which belongs at 0x08000000 via an external programmer) is refused by its 0xff-padding structure, a non-RISC-V image (the 8051 CH549 firmware in the same directory) is refused, and the version is read out of the USB device descriptor the image carries (`bcdDevice`, BCD - `0x0222` = 2.22). The probe model cannot be told from an image (all of them carry product string "WCH-Link"), so that is a warning rather than a check. The ack timeout is 3 s because the probe stalls ~170 ms every 64 write packets while it programs - a 100 ms timeout would fail on every 64th transfer. Verified on a real WCH-LinkE over usbipd/WSL: two full round trips 2.22 -> 2.13 -> 2.22, each reporting the new version after re-enumeration, with a write stream identical to WCH's own (1,826 + 1,826 transfers, all 3,653 acks `0000`, both passes byte-identical to the image). New protocol section docs/protocol/wch-link.ja.md §6.1.
- (JA) `probe firmware update --image <FILE>` を実装(従来は exit 70 のスタブ): WCH の IAP 経路で **probe 自身の firmware** を書き換える。`81 0f 01 01` を送り、`4348:55e0` として再列挙するのを待ち、bulk `0x02`/`0x82` に 60 byte frame で image を 2 回(書込 pass + 照合 pass)流し、終了後に戻ってきた probe の版を報告する。これができるのは WCH の WCH-LinkUtility(Windows 専用)だけだった(probe-rs / wlink / minichlink は probe firmware を更新しない)ので、**Linux / macOS から WCH-LinkE の更新・ダウングレード・IAP 滞留からの救出ができる**ようになった。既に IAP mode の個体はそのまま書ける(entry 不要)ため、中断した更新の復旧が同じコマンドで済む。image は送信前に検査する: BL 付き `*_APP_IAP.bin`(外部書込機で 0x08000000 に焼くもの)は 0xff padding の構造で拒否、非 RISC-V image(同じディレクトリにある 8051 の CH549 firmware)も拒否、版は image 内の USB device descriptor の `bcdDevice`(BCD。`0x0222` = 2.22)から読む。probe 型番は image から判別できない(全機種 product string が "WCH-Link")ため、検査ではなく警告にした。ack の timeout は 3 s: probe は書込中 64 packet ごとに ~170 ms 止まるので、100 ms 固定では 64 転送ごとに必ず失敗する。WCH-LinkE 実機(usbipd/WSL 経由)で検証: 2.22 → 2.13 → 2.22 の往復を 2 度、いずれも再列挙後に新しい版を報告。転送列は純正と同一(書込 1,826 + 照合 1,826、ack 3,653 個すべて `0000`、両 pass とも image とバイト一致)。protocol は docs/protocol/wch-link.ja.md §6.1 を新設。

## 0.5.0 - 2026-09-03

- (EN) `read --region <code|ram|option>[+off[+len]]` is implemented (was a stub that errored "not available until the target DB is generated"). `code` is the flash base 0x0800_0000 with the probe-reported flash size as the default length, `ram` is 0x2000_0000 with the DB SRAM size, `option` is the 16 option bytes at 0x1FFF_F800; `system`/`eeprom` are family-specific and still ask for an explicit `--range`. So `read --region code -o backup.bin` now backs up all of flash without hand-computing the size. Also fixes `read` timing out on a large range: the fast bulk read is now chunked (32 KiB), so a full-flash read (e.g. 288 KiB on a CH32V307) completes in seconds instead of falling back to slow word-by-word DMI reads and hitting the transport timeout. Region resolution is now one shared resolver used by `read` / `erase` / `write` (a single source of truth for the region base addresses); `erase --region` gives a clear "flash only" error for a non-flash region.
- (JA) `read --region <code|ram|option>[+off[+len]]` を実装(従来は「target DB 未生成」で失敗するスタブ)。`code`=flash 先頭 0x0800_0000(既定長=probe 報告の flash 容量)、`ram`=0x2000_0000(長さ=DB の SRAM)、`option`=0x1FFF_F800 の 16 byte。`system`/`eeprom` は family 依存なので `--range` を要求。これで `read --region code -o backup.bin` が容量を手計算せず全 flash を退避できる。あわせて `read` の大範囲タイムアウトを修正: 高速バルク read を 32 KiB 単位で chunk 化し、全 flash 読み(V307 の 288 KiB 等)が数秒で完了する(従来は遅い DMI word 読みへ落ちて timeout していた)。
- (EN) `probe list --watch` is implemented (was a stub): it polls enumeration and prints a `+`/`-` line as WCH-Link / ISP devices are plugged/unplugged, until Ctrl-C. Human-only (a live event stream is not a single JSON object; `probe list --json` without `--watch` gives a snapshot).
- (JA) `probe list --watch` を実装(従来スタブ): 列挙を poll し、WCH-Link / ISP device の挿抜を `+`/`-` 行で Ctrl-C まで表示する。人間向け専用(live ストリームは単一 JSON でないため。スナップショットは `--watch` 無しの `probe list --json`)。
- (EN) `--replay <capture.ndjson>` runs a command against a recorded USB session instead of hardware (the counterpart of `--capture`), so the WCH-Link / DMI protocol layers can be exercised, regression-tested, and bug-reproduced with no probe attached - e.g. a capture of a failing operation from another machine can be analysed and re-run offline. `--capture` now also records the device identity (a `_device` line), which `--replay` uses to reconstruct `enumerate()`; each channel/direction is served as an independent FIFO in the recorded order, and a write whose bytes differ from the recording (or a read past the log) is reported as a divergence warning at the end - a signal that the code now produces a different protocol than the capture. Mutually exclusive with `--capture`. Verified on real hardware: captures of `target info` / `probe info` / `read` on a CH32V307 replay byte-identically offline (same JSON, same SKU/chip-id resolution), with committed fixtures under `tests/fixtures/replay/` driving offline CI regression tests.
- (JA) `--replay <capture.ndjson>` で、記録した USB セッションに対して(実機でなく)コマンドを動かせる(`--capture` の対)。WCH-Link / DMI protocol 層を probe 無しで動かし、回帰テスト・バグ再現ができる - 例えば別マシンから送られた失敗操作の capture を offline で解析・再実行できる。`--capture` は device 識別子(`_device` 行)も記録するようになり、`--replay` がそれで `enumerate()` を再構成する。各 channel×方向を記録順の独立 FIFO で供給し、記録と異なる write(やログ超過の read)は末尾で divergence 警告として報告する(=コードが capture と違う protocol を出した合図)。`--capture` と排他。実機検証: CH32V307 の `target info` / `probe info` / `read` の capture が offline で byte 完全一致再生(同一 JSON・同一 SKU/chip-id 解決)。`tests/fixtures/replay/` の committed fixture が offline CI 回帰テストを駆動する。

## 0.4.1 - 2026-09-03

- (EN) Fix: `flash --verify readback` no longer reports a false `verify-mismatch` (exit 30) on the CH549 Link (WCH-Link, fw 2.12). Its fast bulk read can return a stale, pre-program view of flash (0xff or a garbage ramp) in the moment right after the loader stub runs - the write actually landed, but the in-flash readback disagreed (~2-3 of every ~7 flashes on the CH549; never seen on a WCH-LinkE). The readback now re-checks any fast-read disagreement against the authoritative DMI read (progbuf word reads, through the real bus), so a stale fast read is corrected while a genuine mismatch is still caught. A pre-0.4.0-behaviour regression introduced with the 0.4.0 fast bulk read; reproduced and fixed on a real CH549 (15/15 flashes clean, ~2/12 stale fast reads silently corrected). LinkE flashing is unaffected.
- (JA) 修正: CH549 Link(WCH-Link、fw 2.12)で `flash --verify readback` が偽の `verify-mismatch`(exit 30)を報告しなくなった。CH549 の fast bulk read は loader stub 実行直後の一瞬、program 前の stale な flash view(0xff やゴミの ramp)を返すことがあり、書込は成功しているのに in-flash readback が食い違っていた(CH549 で ~7 回中 2-3 回、WCH-LinkE では未発生)。readback は fast read の不一致を権威ある DMI 読み(progbuf の word 読み、実バス経由)で再確認するようにし、stale な fast read は訂正、真の不一致は従来どおり検出する。0.4.0 の fast bulk read 導入で入った回帰。実 CH549 で再現・修正(15/15 clean、~2/12 の stale fast read を無言で訂正)。LinkE の書込は影響なし。

## 0.4.0 - 2026-09-03

- (EN) **Consistency sweep (breaking; JSON contract bumped 1 -> 2).** A pre-1.0 pass to unify the API/JSON/exit-code surface while breaking changes are still cheap (docs/consistency-audit.ja.md). Library: one canonical `FlashParams` (owned by `ch32rv-wchlink`; `ch32rv-flash::params_for_family` returns it, and `code_flash_start` is now the constant `ch32rv_flash::CODE_FLASH_START`); the byte-range memory read is `read_mem` on both `WchLink` and the Debug Module, and `WchLink::write_flash(addr, data, ...)` now takes the address first, matching the DMI writers; flash sizes are bytes throughout (`ChipInfo.flash_bytes: u32`, `SkuRecord.flash_bytes/sram_bytes: u32`); `capture::{record, Chan, Dir}` are now `pub(crate)`. JSON (`--json`): flash size is `flash_bytes` (was `flash_kb`); memory address keys are `addr` (were `start`); erase scope is `scope` (was `erase` on `flash`); a readback match is `verified` (was `verify`/`match`); `probe firmware info` reports `firmware`/`firmware_mode` (were `version`/`mode`); `recover` reports `family` (was `chip`); on/off states are booleans (`read_protected`, `probe power` -> `{rail, on}`); `probe list` per-probe failures use `probe_error`; duplicated envelope fields (`result.ok`, `result.contract`) were dropped; `dbg reg/dmi write` and `target protect` no-ops now emit an envelope under `--json`. Exit codes: a new `transfer-failed` (40) kind separates flash/DMI operation failures from a genuine `transport-timeout` (also 40); `13`/`device-busy` is reserved for the advisory-lock timeout and a typed USB-claimed error (no more substring matching); a no-response attach is `target-no-response` (20, was 22); `target option set` fails `verify-mismatch` (30) when a write does not read back (was a silent success); `run`'s unexpected halt is `not-running-after-write` (50, was 22); filesystem and USB-enumeration errors no longer map to the internal-bug code (70). CLI flags: `flash`/`verify` load address is `--at` (was `--offset`, matching `write`); a new global `--duration` sets how long `monitor`/`run` stream (was the overloaded `--timeout`, which is now transport-only); `run --exit-on` is an enum `semihosting|timeout` (was a hand-parsed `timeout=<s>`); `read --format hex-dump` renamed from `hex` so `hex`/`ihex` mean Intel HEX consistently.

- (EN) `monitor --source rtt` (was a stub) reads a SerialRTT / SEGGER-format channel out of the target's RAM: it scans RAM for the control-block magic, validates a candidate by its up[0] descriptor (buffer pointer in RAM, sane size and offsets - so a stray copy of the magic inside a ring buffer is not mistaken for a block), then drains the up (target->host) ring and streams it to stdout, writing the read offset back so the target keeps producing. The control-block scan length comes from the target's SRAM size (DB) or an 8 KiB default, read in 8 KiB chunks so the probe's bulk read never sees an oversized region. Verified on a CH32V307 running the core's SerialRTT HelloRTT: the block was found at 0x20000018 and `hello from RAM` + the `uptime N s` stream came through live. New fixture `tests/fixtures/rtt-ch32v307.bin`.

- (JA) `probe mode set <riscv|dap>`(従来 stub)で WCH-LinkE を RISC-V↔DAP/ARM モード切替。RISC-V→DAP は probe へ `81 ff 01 41`、DAP→RISC-V は DAP デバイスの interface 0 OUT endpoint へ `81 ff 01 52`。probe は再列挙する(USB PID 0x8010↔0x8012)ので WCH-LinkE 限定(CH549 は fail-closed)、切替前に確認(`--yes` で省略)、再列挙を報告し、新 PID が再出現したら新モードを確認する。両方向を WCH-LinkE で実機検証。現在の設定値の読み出しは従来どおり `probe info` / `probe mode get` / `probe firmware info`。
- (EN) Memory reads are now roughly two orders of magnitude faster: `read`, `verify`, `flash --preverify`, and the default `flash --verify readback` use the WCH-Link's bulk memory-read (SetReadMemoryRegion + Program ReadMemory + data-endpoint stream, byte-order corrected) instead of word-by-word DMI reads, falling back to DMI only if the probe rejects a region. New `WchLink::read_mem`. Measured on a WCH-LinkE over usbipd: a 32 KiB read went from a >120 s timeout to 0.71 s (~45 KiB/s), and `flash --verify readback` of 4 KiB from ~15 s to 0.6 s (~25x). Byte-exact (including endianness) on CH32V003 / V103 / V203 / V307 / L103 and the CH549 Link. Writes (flash programming) were already fast via the stub; this closes the gap on the read side, and helps most on high-latency links - usbipd and the Windows WCH-driver ioctl path - where per-word round-trips dominated.
- (JA) メモリ読み出しが約 2 桁高速化: `read` / `verify` / `flash --preverify` と既定の `flash --verify readback` が、word 単位 DMI 読みでなく WCH-Link のバルク memory-read(SetReadMemoryRegion + Program ReadMemory + data endpoint stream、endian 補正)を使うようになった(probe が領域を弾いたときだけ DMI へ fallback)。`WchLink::read_memory` を追加。WCH-LinkE + usbipd 実測: 32 KiB read が >120s タイムアウト→0.71s(~45 KiB/s)、`flash --verify readback` 4 KiB が ~15s→0.6s(~25倍)。CH32V003 / V103 / V203 / V307 / L103 と CH549 Link で byte 完全一致(endian 含む)。書き込み(program)は stub で元々高速だったので、これで read 側の遅さを解消。usbipd や Windows の WCH ドライバ ioctl 経路のような高遅延リンクで特に効く。

## 0.3.0 - 2026-09-02

- (EN) Windows now works with WCH's stock vendor driver - no Zadig/WinUSB replacement (ArduinoCore-CH32 request B-2, Windows). - (EN) `--capture <file>` now records the probe's USB transactions (ArduinoCore-CH32 request A-3): every bulk transfer on the WCH-Link command channel (EP 0x01/0x81) and flash-data channel (EP 0x02/0x82) is appended as one NDJSON line (`seq`, `t_us`, `chan`, `dir`, `len`, `ok`, hex `data`) behind a `_meta` header, so a protocol problem hit on the bench can be reported as a replay fixture instead of "reproduce it on hardware first". The sink lives in `ch32rv-usb` (`capture` module), is set once from `main`, and is a no-op when the flag is absent (zero cost off the flag). Verified on the bench: `target info --capture` produced 12 valid NDJSON transactions of the real GetProbeInfo / SetSpeed / AttachChip exchange.
- (JA) `--capture <file>` が probe の USB transaction を記録するようになった(ArduinoCore-CH32 依頼 A-3): WCH-Link の command channel(EP 0x01/0x81)と flash-data channel(EP 0x02/0x82)の全 bulk 転送を、`_meta` ヘッダの後に NDJSON 1 行ずつ(`seq`・`t_us`・`chan`・`dir`・`len`・`ok`・hex `data`)追記する。ベンチで踏んだ protocol 問題を「実機で再現待ち」でなく replay fixture として報告できる。sink は `ch32rv-usb` の `capture` module にあり `main` が一度設定、flag 無しなら no-op(off 時コストなし)。実機検証: `target info --capture` が実際の GetProbeInfo / SetSpeed / AttachChip のやり取りを 12 件の有効 NDJSON transaction として記録。
- (EN) `--lock-timeout` now backs a real per-probe advisory lock (docs/cli.ja.md §3.7, ArduinoCore-CH32 request A-2): before a command touches a probe it takes an exclusive OS file lock keyed by the probe serial (or the bus topology when it has no serial), so two `ch32rv` processes on the same probe serialize instead of colliding - the bench can run a monitor and an upload against one probe without them stepping on each other. It covers the attach path (`flash` / `target` / `dbg` / `write` / `monitor --source dmdata` / `capabilities` / `arduino`), the `gdb` server, and `monitor --source uart` / `sdi`, each holding the lock for the operation's duration. A process that cannot take the lock within `--lock-timeout` exits 13 (`device-busy`). The lock is an `flock`, so the OS releases a crashed holder's lock automatically (no stale-lock sweep). New `ch32rv-usb` `DeviceLock`. Verified on the bench: with one probe held by a `uart` monitor, a second command on that probe exits 13 while a command on a different probe is unaffected, and the probe is usable again once the holder releases.
- (JA) `--lock-timeout` が実際の probe 単位 advisory lock を駆動するようになった(docs/cli.ja.md §3.7、ArduinoCore-CH32 依頼 A-2): probe に触れる前に probe serial(無ければ bus topology)をキーに OS の排他ファイル lock を取り、同一 probe への 2 つの `ch32rv` プロセスを衝突でなく直列化する - ベンチが 1 台の probe に monitor と upload を並行させても踏み合わない。対象は attach 経路(`flash` / `target` / `dbg` / `write` / `monitor --source dmdata` / `capabilities` / `arduino`)、`gdb` server、`monitor --source uart` / `sdi` で、各操作の間だけ保持。`--lock-timeout` 内に取れなければ exit 13(`device-busy`)。lock は `flock` なので保持者が異常終了しても OS が自動解放(stale 掃除不要)。`ch32rv-usb` に `DeviceLock` を追加。実機検証: 1台の probe を `uart` monitor が保持した状態で、その probe への2つ目のコマンドは exit 13、別 probe は無影響、保持者が解放すれば再び使用可。
