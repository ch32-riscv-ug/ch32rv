# Changelog

## Unreleased

## 0.4.0 - 2026-09-03

- (EN) **Consistency sweep (breaking; JSON contract bumped 1 -> 2).** A pre-1.0 pass to unify the API/JSON/exit-code surface while breaking changes are still cheap (docs/consistency-audit.ja.md). Library: one canonical `FlashParams` (owned by `ch32rv-wchlink`; `ch32rv-flash::params_for_family` returns it, and `code_flash_start` is now the constant `ch32rv_flash::CODE_FLASH_START`); the byte-range memory read is `read_mem` on both `WchLink` and the Debug Module, and `WchLink::write_flash(addr, data, ...)` now takes the address first, matching the DMI writers; flash sizes are bytes throughout (`ChipInfo.flash_bytes: u32`, `SkuRecord.flash_bytes/sram_bytes: u32`); `capture::{record, Chan, Dir}` are now `pub(crate)`. JSON (`--json`): flash size is `flash_bytes` (was `flash_kb`); memory address keys are `addr` (were `start`); erase scope is `scope` (was `erase` on `flash`); a readback match is `verified` (was `verify`/`match`); `probe firmware info` reports `firmware`/`firmware_mode` (were `version`/`mode`); `recover` reports `family` (was `chip`); on/off states are booleans (`read_protected`, `probe power` -> `{rail, on}`); `probe list` per-probe failures use `probe_error`; duplicated envelope fields (`result.ok`, `result.contract`) were dropped; `dbg reg/dmi write` and `target protect` no-ops now emit an envelope under `--json`. Exit codes: a new `transfer-failed` (40) kind separates flash/DMI operation failures from a genuine `transport-timeout` (also 40); `13`/`device-busy` is reserved for the advisory-lock timeout and a typed USB-claimed error (no more substring matching); a no-response attach is `target-no-response` (20, was 22); `target option set` fails `verify-mismatch` (30) when a write does not read back (was a silent success); `run`'s unexpected halt is `not-running-after-write` (50, was 22); filesystem and USB-enumeration errors no longer map to the internal-bug code (70). CLI flags: `flash`/`verify` load address is `--at` (was `--offset`, matching `write`); a new global `--duration` sets how long `monitor`/`run` stream (was the overloaded `--timeout`, which is now transport-only); `run --exit-on` is an enum `semihosting|timeout` (was a hand-parsed `timeout=<s>`); `read --format hex-dump` renamed from `hex` so `hex`/`ihex` mean Intel HEX consistently.
- (JA) **一貫性スイープ(破壊的。JSON contract を 1 -> 2 へ)。** 破壊変更が安価な 1.0 前に API/JSON/exit-code の面を統一(docs/consistency-audit.ja.md)。ライブラリ: `FlashParams` を 1 つに正準化(`ch32rv-wchlink` 所有。`ch32rv-flash::params_for_family` がそれを返し、`code_flash_start` は定数 `ch32rv_flash::CODE_FLASH_START` に)。byte 範囲メモリ読みは `WchLink`・Debug Module 両方で `read_mem`、`WchLink::write_flash(addr, data, ...)` は DMI writer に合わせて addr 先。flash サイズは一貫して bytes(`ChipInfo.flash_bytes: u32`、`SkuRecord.flash_bytes/sram_bytes: u32`)。`capture::{record, Chan, Dir}` は `pub(crate)`。JSON: flash サイズ `flash_bytes`(旧 `flash_kb`)、番地キー `addr`(旧 `start`)、erase scope `scope`(flash の旧 `erase`)、readback 一致 `verified`(旧 `verify`/`match`)、`probe firmware info` は `firmware`/`firmware_mode`(旧 `version`/`mode`)、`recover` は `family`(旧 `chip`)、on/off は bool(`read_protected`、`probe power` は `{rail, on}`)、`probe list` の probe 別失敗は `probe_error`、envelope 重複(`result.ok`/`result.contract`)を削除、`dbg reg/dmi write` と `target protect` の no-op も `--json` で envelope を出す。exit code: `transfer-failed`(40)を新設し flash/DMI 操作失敗を真の `transport-timeout`(同 40)と区別、`13`/`device-busy` は advisory-lock timeout と型付き USB-claimed 専用(部分文字列一致を廃止)、無応答 attach は `target-no-response`(20、旧 22)、`target option set` は書込が読み戻せないと `verify-mismatch`(30、旧 silent success)、`run` の異常 halt は `not-running-after-write`(50、旧 22)、filesystem/USB 列挙エラーを内部バグコード(70)から分離。CLI: `flash`/`verify` のロード番地は `--at`(旧 `--offset`、`write` に統一)、global `--duration` を新設し `monitor`/`run` の実行長に(過負荷だった `--timeout` は transport 専用に)、`run --exit-on` は enum `semihosting|timeout`(旧手書き `timeout=<s>`)、`read --format hex-dump`(旧 `hex`)で `hex`/`ihex` は Intel HEX 一意に。
- (EN) `recover --method unbrick` (was a stub) is the attach-based one-shot recovery: it attaches the target and then clears whatever keeps it from a normal flash - read protection (writes factory option bytes, which triggers the chip's mass erase) when set, otherwise a whole-chip erase - and applies it with a reset, so the operator does not have to first diagnose which case it is. A target that cannot attach at all (its app repurposed SWDIO/SWCLK) is beyond an attach-based fix, so it points at the no-attach `--method power-off --chip <family>`. Prompts before erasing (`--yes`/`--non-interactive` to skip). Verified on a CH32V307: `recover --method unbrick --yes` on an unprotected target ran a whole-chip erase and reset, and the JSON path reports `{action, family, protected}`. The read-protected branch reuses the same factory-option-byte primitive that `--method unprotect` already verified.
- (JA) `recover --method unbrick`(従来 stub)が attach ベースの一撃復旧になった: target に attach し、通常 flash を妨げているもの(保護 ON なら工場 option bytes 書込=chip の mass erase を誘発、そうでなければ chip erase)をクリアして reset で反映する。operator がどの状況かを先に切り分けなくてよい。全く attach できない target(app が SWDIO/SWCLK を転用)は attach ベースでは直せないので、非 attach の `--method power-off --chip <family>` を案内する。消去前に確認(`--yes`/`--non-interactive` で省略)。CH32V307 実機検証: 未保護 target への `recover --method unbrick --yes` が chip erase + reset を実行、JSON は `{action, family, protected}` を報告。読み出し保護の分岐は `--method unprotect` で検証済みの工場 option byte 書込 primitive を再利用。
- (EN) `monitor --source rtt` (was a stub) reads a SerialRTT / SEGGER-format channel out of the target's RAM: it scans RAM for the control-block magic, validates a candidate by its up[0] descriptor (buffer pointer in RAM, sane size and offsets - so a stray copy of the magic inside a ring buffer is not mistaken for a block), then drains the up (target->host) ring and streams it to stdout, writing the read offset back so the target keeps producing. Reading RAM and writing the offset both go over the Debug Module, which needs the hart halted, so this backend briefly halts the core once per poll (~50 ms cadence) - unlike probe-rs's background access, so the target's timers drift slightly while a monitor is attached (`dmdata` stays the zero-halt option). The control-block scan length comes from the target's SRAM size (DB) or an 8 KiB default, read in 8 KiB chunks so the probe's bulk read never sees an oversized region. Verified on a CH32V307 running the core's SerialRTT HelloRTT: the block was found at 0x20000018 and `hello from RAM` + the `uptime N s` stream came through live. New fixture `tests/fixtures/rtt-ch32v307.bin`.
- (JA) `monitor --source rtt`(従来 stub)が SerialRTT / SEGGER 形式チャンネルを target の RAM から読む: RAM を control block の magic で走査し、候補を up[0] descriptor(buffer が RAM 内・size と offset が妥当)で検証(リングバッファ内の magic の紛れ込みを block と誤認しない)、up(target→host)リングを汲んで stdout へ流し、read offset を書き戻して target が出力を続けられるようにする。RAM 読みと offset 書戻しは DM 経由=hart halt 要なので poll(~50ms 間隔)ごとに一瞬 halt する - probe-rs の background access と違い target のタイマが僅かにドリフトする(`dmdata` は halt 無しの選択肢のまま)。走査長は target の SRAM サイズ(DB)か既定 8 KiB で、8 KiB chunk 読みなので probe のバルク read が過大領域を見ない。CH32V307 + core の SerialRTT HelloRTT で検証: block を 0x20000018 で発見、`hello from RAM` + `uptime N s` を live 受信。新 fixture `tests/fixtures/rtt-ch32v307.bin`。
- (EN) `run <ELF|bin>` (was a stub) is the one-command HIL runner: it flashes the image (skip with `--no-flash`), resets the target to run, streams its runtime output, and ends on a chosen condition. `--exit-on semihosting` hosts RISC-V semihosting - it forwards `SYS_WRITE0`/`SYS_WRITEC` output and propagates the target's `SYS_EXIT`/`SYS_EXIT_EXTENDED` code as the process exit code (a plain `SYS_EXIT` with reason `ADP_Stopped_ApplicationExit` = exit 0), bounded by a safety `--duration` (default 60 s; a timeout exits `transport-timeout`). `--exit-on timeout --duration <s>` streams dmdata output for s seconds then exits 0; with no `--exit-on` it streams until `--duration`/Ctrl-C. Output currently comes via `--source dmdata` (uart/sdi/rtt are a follow-up). Verified on a CH32V307: the new `tests/fixtures/semihosting.bin` printed `hello from semihosting` and exited 42; a plain `SYS_EXIT`/`ADP_Stopped_ApplicationExit` build exited 0; the safety cap and `--no-flash`/`--json` paths behave.
- (JA) `run <ELF|bin>`(従来 stub)が 1 コマンドの HIL ランナーになった: image を書込(`--no-flash` で省略)、target を reset 実行、runtime 出力を流し、指定条件で終わる。`--exit-on semihosting` は RISC-V semihosting をホストする - `SYS_WRITE0`/`SYS_WRITEC` の出力を中継し、target の `SYS_EXIT`/`SYS_EXIT_EXTENDED` の値をプロセス終了コードに伝搬する(reason が `ADP_Stopped_ApplicationExit` の素の `SYS_EXIT` は exit 0)。安全弁として `--duration`(既定 60 秒、超過は `transport-timeout` で終了)。`--exit-on timeout --duration <s>` は dmdata 出力を s 秒流して exit 0、`--exit-on` 無しなら `--duration`/Ctrl-C まで流す。出力は現状 `--source dmdata` 経由(uart/sdi/rtt は後続)。CH32V307 実機検証: 新規 `tests/fixtures/semihosting.bin` が `hello from semihosting` を出力して exit 42、素の `SYS_EXIT`/`ADP_Stopped_ApplicationExit` ビルドは exit 0、安全 cap と `--no-flash`/`--json` も期待通り。
- (EN) `probe power 3v3|5v <on|off>` and `probe power cycle [--off-ms <n>]` (were stubs) control the WCH-LinkE target-power output (SetPower, cmd 0x0d: 3v3 on=`09`/off=`0a`, 5v on=`0b`/off=`0c`; cycle drops and restores 3v3). WCH-LinkE only - the CH549 Link fails closed. Verified at the command level on a WCH-LinkE (all four rail/state combinations and cycle accepted; the CH549 rejected with `capability-unsupported`); the actual output voltage needs a meter or a probe-powered target to confirm.
- (JA) `probe power 3v3|5v <on|off>` と `probe power cycle [--off-ms <n>]`(従来 stub)で WCH-LinkE の target 給電出力を制御(SetPower、cmd 0x0d: 3v3 on=`09`/off=`0a`、5v on=`0b`/off=`0c`、cycle は 3v3 を落として戻す)。WCH-LinkE 限定で CH549 は fail-closed。WCH-LinkE でコマンドレベル検証(4 組合せ + cycle が受理、CH549 は `capability-unsupported` で拒否)。実出力電圧は計測器か probe 給電の target が要る。
- (EN) `probe mode set <riscv|dap>` (was a stub) switches a WCH-LinkE between RISC-V and DAP/ARM mode. RISC-V->DAP sends `81 ff 01 41` to the probe; DAP->RISC-V sends `81 ff 01 52` to the DAP device's interface-0 OUT endpoint. The probe re-enumerates (USB PID 0x8010 <-> 0x8012), so it is WCH-LinkE only (the CH549 Link fails closed), prompts before switching (`--yes` skips), and reports the re-enumeration; when the re-enumerated PID reappears it confirms the new mode. Verified both directions on a WCH-LinkE. Reading the current probe settings is unchanged: `probe info` / `probe mode get` / `probe firmware info`.
- (JA) `probe mode set <riscv|dap>`(従来 stub)で WCH-LinkE を RISC-V↔DAP/ARM モード切替。RISC-V→DAP は probe へ `81 ff 01 41`、DAP→RISC-V は DAP デバイスの interface 0 OUT endpoint へ `81 ff 01 52`。probe は再列挙する(USB PID 0x8010↔0x8012)ので WCH-LinkE 限定(CH549 は fail-closed)、切替前に確認(`--yes` で省略)、再列挙を報告し、新 PID が再出現したら新モードを確認する。両方向を WCH-LinkE で実機検証。現在の設定値の読み出しは従来どおり `probe info` / `probe mode get` / `probe firmware info`。
- (EN) Memory reads are now roughly two orders of magnitude faster: `read`, `verify`, `flash --preverify`, and the default `flash --verify readback` use the WCH-Link's bulk memory-read (SetReadMemoryRegion + Program ReadMemory + data-endpoint stream, byte-order corrected) instead of word-by-word DMI reads, falling back to DMI only if the probe rejects a region. New `WchLink::read_mem`. Measured on a WCH-LinkE over usbipd: a 32 KiB read went from a >120 s timeout to 0.71 s (~45 KiB/s), and `flash --verify readback` of 4 KiB from ~15 s to 0.6 s (~25x). Byte-exact (including endianness) on CH32V003 / V103 / V203 / V307 / L103 and the CH549 Link. Writes (flash programming) were already fast via the stub; this closes the gap on the read side, and helps most on high-latency links - usbipd and the Windows WCH-driver ioctl path - where per-word round-trips dominated.
- (JA) メモリ読み出しが約 2 桁高速化: `read` / `verify` / `flash --preverify` と既定の `flash --verify readback` が、word 単位 DMI 読みでなく WCH-Link のバルク memory-read(SetReadMemoryRegion + Program ReadMemory + data endpoint stream、endian 補正)を使うようになった(probe が領域を弾いたときだけ DMI へ fallback)。`WchLink::read_memory` を追加。WCH-LinkE + usbipd 実測: 32 KiB read が >120s タイムアウト→0.71s(~45 KiB/s)、`flash --verify readback` 4 KiB が ~15s→0.6s(~25倍)。CH32V003 / V103 / V203 / V307 / L103 と CH549 Link で byte 完全一致(endian 含む)。書き込み(program)は stub で元々高速だったので、これで read 側の遅さを解消。usbipd や Windows の WCH ドライバ ioctl 経路のような高遅延リンクで特に効く。

## 0.3.0 - 2026-09-02

- (EN) Windows now works with WCH's stock vendor driver - no Zadig/WinUSB replacement (ArduinoCore-CH32 request B-2, Windows). New crate `ch32rv-usb-wch-win` talks to the driver (`WCHLinkW64.SYS`, CH375-family `DeviceIoControl`) from 64-bit Rust without the 32-bit-only `WCHLinkDLL.dll`; it is protocol-agnostic on purpose - device-interface enumeration by GUID, open, endpoint-addressed bulk transfers, and a parent-instance-ID helper for serial correlation - so other Rust tools can reuse it as a component. `ch32rv-usb` gained a per-device fallback: when nusb cannot open an interface (typically because the WCH driver owns it), it finds the same serial on the CH375 side and opens that instead, so ch32rv and WCH-LinkUtility coexist on one machine. Verified live on Windows 11 with the stock driver on all 5 bench probes: `probe list` / `probe info` (CH549 fw 2.12 + LinkE fw 2.22), full-stack `target info`, and a complete flash round trip (read backup ×2, chip erase, program, readback verify) on CH32V003 / V103 / L103 / V203 / V307 — including multi-packet data-endpoint writes (128/256-byte stub packets chunked to the driver's 64-byte ioctl). Known characteristic: this path is slow (~2.3 KiB/s reads; one ioctl moves at most 64 bytes).
- (JA) Windows が WCH 純正ドライバのまま動くようになった - Zadig/WinUSB 置換不要(ArduinoCore-CH32 依頼 B-2 の Windows 対応)。新 crate `ch32rv-usb-wch-win` が純正ドライバ(`WCHLinkW64.SYS`、CH375 系 `DeviceIoControl`)を 64bit Rust から直接叩く(32bit 限定の `WCHLinkDLL.dll` 不要)。意図的に protocol 非依存 - GUID による device interface 列挙、open、endpoint 番号指定の bulk 転送、serial 突き合わせ用の親 instance ID ヘルパ - なので他の Rust 製ツールも部品として再利用できる。`ch32rv-usb` には device 単位のフォールバックを追加: nusb で interface を開けない場合(典型: WCH ドライバが所有)、CH375 側で同一 serial を見つけてそちらを開くため、ch32rv と WCH-LinkUtility が同一マシンで共存できる。Windows 11 純正ドライバ実機検証(ベンチ全 5 probe): `probe list` / `probe info`(CH549 fw 2.12 + LinkE fw 2.22)、`target info` のフルスタック動作、および CH32V003 / V103 / L103 / V203 / V307 での flash 完全往復(read backup ×2 → chip erase → program → readback verify)。data endpoint の複数 packet 書込(stub の 128/256B packet をドライバの 64B ioctl に分割)も検証済み。既知の特性: この経路は遅い(read ~2.3 KiB/s。1 ioctl 最大 64B のため)。

- (EN) `--capture <file>` now records the probe's USB transactions (ArduinoCore-CH32 request A-3): every bulk transfer on the WCH-Link command channel (EP 0x01/0x81) and flash-data channel (EP 0x02/0x82) is appended as one NDJSON line (`seq`, `t_us`, `chan`, `dir`, `len`, `ok`, hex `data`) behind a `_meta` header, so a protocol problem hit on the bench can be reported as a replay fixture instead of "reproduce it on hardware first". The sink lives in `ch32rv-usb` (`capture` module), is set once from `main`, and is a no-op when the flag is absent (zero cost off the flag). Verified on the bench: `target info --capture` produced 12 valid NDJSON transactions of the real GetProbeInfo / SetSpeed / AttachChip exchange.
- (JA) `--capture <file>` が probe の USB transaction を記録するようになった(ArduinoCore-CH32 依頼 A-3): WCH-Link の command channel(EP 0x01/0x81)と flash-data channel(EP 0x02/0x82)の全 bulk 転送を、`_meta` ヘッダの後に NDJSON 1 行ずつ(`seq`・`t_us`・`chan`・`dir`・`len`・`ok`・hex `data`)追記する。ベンチで踏んだ protocol 問題を「実機で再現待ち」でなく replay fixture として報告できる。sink は `ch32rv-usb` の `capture` module にあり `main` が一度設定、flag 無しなら no-op(off 時コストなし)。実機検証: `target info --capture` が実際の GetProbeInfo / SetSpeed / AttachChip のやり取りを 12 件の有効 NDJSON transaction として記録。
- (EN) `--lock-timeout` now backs a real per-probe advisory lock (docs/cli.ja.md §3.7, ArduinoCore-CH32 request A-2): before a command touches a probe it takes an exclusive OS file lock keyed by the probe serial (or the bus topology when it has no serial), so two `ch32rv` processes on the same probe serialize instead of colliding - the bench can run a monitor and an upload against one probe without them stepping on each other. It covers the attach path (`flash` / `target` / `dbg` / `write` / `monitor --source dmdata` / `capabilities` / `arduino`), the `gdb` server, and `monitor --source uart` / `sdi`, each holding the lock for the operation's duration. A process that cannot take the lock within `--lock-timeout` exits 13 (`device-busy`). The lock is an `flock`, so the OS releases a crashed holder's lock automatically (no stale-lock sweep). New `ch32rv-usb` `DeviceLock`. Verified on the bench: with one probe held by a `uart` monitor, a second command on that probe exits 13 while a command on a different probe is unaffected, and the probe is usable again once the holder releases.
- (JA) `--lock-timeout` が実際の probe 単位 advisory lock を駆動するようになった(docs/cli.ja.md §3.7、ArduinoCore-CH32 依頼 A-2): probe に触れる前に probe serial(無ければ bus topology)をキーに OS の排他ファイル lock を取り、同一 probe への 2 つの `ch32rv` プロセスを衝突でなく直列化する - ベンチが 1 台の probe に monitor と upload を並行させても踏み合わない。対象は attach 経路(`flash` / `target` / `dbg` / `write` / `monitor --source dmdata` / `capabilities` / `arduino`)、`gdb` server、`monitor --source uart` / `sdi` で、各操作の間だけ保持。`--lock-timeout` 内に取れなければ exit 13(`device-busy`)。lock は `flock` なので保持者が異常終了しても OS が自動解放(stale 掃除不要)。`ch32rv-usb` に `DeviceLock` を追加。実機検証: 1台の probe を `uart` monitor が保持した状態で、その probe への2つ目のコマンドは exit 13、別 probe は無影響、保持者が解放すれば再び使用可。

## 0.2.0 - 2026-09-02

- (EN) Initial release. `ch32rv` flashes and debugs WCH CH32 RISC-V MCUs over WCH-Link / WCH-LinkE, shipped as a CLI (`cargo install ch32rv`) and as reusable library crates. Verified on a six-board bench (CH32V003 / V103 / V203 / V307 / X035 / L103). Prebuilt binaries for Linux / macOS / Windows - Linux x86_64 is verified, the others are experimental.
- (JA) 初回リリース。`ch32rv` は WCH-Link / WCH-LinkE 経由で WCH CH32 RISC-V MCU を書き込み・デバッグするツール。CLI(`cargo install ch32rv`)と再利用可能な library crate として配布。6台ベンチ(CH32V003 / V103 / V203 / V307 / X035 / L103)で実機検証。Linux / macOS / Windows のバイナリを配布 - Linux x86_64 = verified、他は experimental。
- (EN) Release artifacts unpack into a single `ch32rv-<version>-<target>/` directory bundling the binary + LICENSE + README + CHANGELOG - arduino-cli requires the root directory, and a correctly-rooted upstream lets downstream mirrors pass the bytes through byte-identical (their provenance checksum still matches). `version --json` now reports the embedded device-DB provenance under `target_db` (`source_rev` = the `ch32-device-data` revision, plus an fnv1a64 `digest` of the embedded rows, same fingerprint convention as `flash_stub_digest`), wiring the docs/architecture.ja.md §3 reproducibility contract.
- (JA) リリース成果物は単一の `ch32rv-<version>-<target>/` ディレクトリに展開され、binary + LICENSE + README + CHANGELOG を同梱する - arduino-cli がルートディレクトリを要求し、正しく root 付きの upstream は下流 mirror がバイト同一で素通しできる(provenance checksum が一致し続ける)。`version --json` は埋め込み device DB の来歴を `target_db` で報告するようになった(`source_rev` = `ch32-device-data` の revision、加えて埋め込み行の fnv1a64 `digest`。`flash_stub_digest` と同じ指紋方式)。docs/architecture.ja.md §3 の再現性契約を配線。
- (EN) The udev rule for non-root WCH-Link access now lives in one file (`cli/60-ch32rv.rules`): `doctor --emit-udev` prints it verbatim (`include_str!`) and the Linux tarball bundles it, so the two never drift (ArduinoCore-CH32 request B-6). `uaccess` is the primary grant with a `plugdev`/`0660` fallback; it covers the WCH-Link RISC-V (8010/8011) and DAP (8012) PIDs.
