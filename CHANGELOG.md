# Changelog

## Unreleased

- (EN) Fix: `monitor --source sdi --duration N` now ends after N seconds even when the target prints nothing. The SDI stream reads the probe's CDC port with a plain blocking read - it has to: opening it non-blocking, or through the serialport crate, makes the WCH-LinkE stop forwarding after one line - and the deadline was only checked after a read returned, so a silent target kept the command open until something arrived: `--duration 4` ran for 34.8 s on a CH32L103 (reported from the ArduinoCore-CH32 bench). The read now runs on a thread of its own and the stream waits on it with a timeout, so the fd stays exactly as it was. Verified on a WCH-LinkE: an erased (silent) CH32L103 stops at 4.0 s after the 0.27 s setup, 3/3, and a CH32V203 running `SerialSDI`'s HelloSDI streams as before, its uptime counter strictly consecutive with no duplicate or missing line.
- (JA) 修正: `monitor --source sdi --duration N` が、target が何も印字しなくても N 秒で終わるようになった。SDI の stream は probe の CDC port を素のブロッキング read で読む(そうしなければならない: 非ブロッキングで開くか serialport crate で開くと、WCH-LinkE は 1 行で forward を止める)が、締め切りを read が戻った後にしか確認していなかったため、無音の target では何か届くまでコマンドが終わらなかった — CH32L103 で `--duration 4` が 34.8 秒続いた(ArduinoCore-CH32 のベンチから報告)。read を専用スレッドに移し、stream は timeout 付きでそれを待つようにした(fd の扱いは一切変えていない)。WCH-LinkE で確認: 消去済み(無音)の CH32L103 は準備 0.27 秒のあと 4.0 秒ちょうどで止まる(3/3)、`SerialSDI` の HelloSDI を走らせた CH32V203 は従来どおり流れ、uptime の番号は重複も欠落もなく連続。

- (EN) `monitor` now warns, with code `attach-reclocks-target`, that attaching through a WCH-Link reprograms the target's clock and does not restore it: the firmware being watched keeps the probe's clock - UART baud rates and timers off - until it resets. ch32rv cannot undo it (the original values are overwritten inside AttachChip, before anything can read them), so the warning says how to watch at the firmware's own clock: `ch32rv run <elf> --no-flash --source dmdata|dmseq|rtt` (attach, reset over DMI, then stream), or the board's reset. Every DMI source and `sdi` attach; only `uart` does not. The CDC path (`uart` / `sdi`) now also prints its warnings in human mode - it used to carry them only in the JSON envelope. `docs/cli.ja.md` §4.5 describes the effect, including on `target info` / `read` / `dbg` / `arduino monitor`, which attach the same way without the warning.

- (EN) Docs: what a WCH-LinkE (fw 2.22) does on the wire, from paired USB + wire captures of every ch32rv operation on a CH32L103 / V203 / V003 (`docs/protocol/wch-link.ja.md` §7a; captures in `wch-protocols`, `captures/fixtures/wire-linke-p4-2026-09-25/`). The ones a user can feel: **AttachChip reprograms the target's clock and does not restore it** - it leaves each family on a fixed PLL setting, writes `RCC_CFGR2` to 0 on V20x without reading it and forces FLASH_ACTLR to `0x1` on L103 - so a running firmware keeps the LinkE's clock after any attach that is not followed by a reset (`monitor`, `target info`, `read`, `dbg`), until it resets; and **flashing zeroes the RCC peripheral clock enables and SysTick without restoring them**, which only the final reset puts right (`flash --reset none` leaves them off). Also recorded: the chip erase is done by the LinkE itself (MER), not by the stub, as `docs/cli.ja.md` had said; the stub ch32rv uploads runs verbatim, with its calling convention observed; the bulk read is an abstract memory access with abstractauto that never checks ABSTRACTCS; the word left in DATA0 after attach is the last ESIG word read (`0x1FFFF7F0`); RedetectChip touches no clock but DMI does not reach the target after it; and one DmiOp is exactly one DMI frame.
- (JA) 文書: WCH-LinkE(fw 2.22)が線上で何をしているかを、ch32rv の全操作を CH32L103 / V203 / V003 で USB と線の両方から同時に収録した capture から記録した(`docs/protocol/wch-link.ja.md` §7a、capture は `wch-protocols` の `captures/fixtures/wire-linke-p4-2026-09-25/`)。利用者に効くもの: **AttachChip は target のクロックを組み直し、元に戻さない** — 系統ごとの決まった PLL 設定にし、V20x では `RCC_CFGR2` を読まずに 0、L103 では FLASH_ACTLR を決め打ちの `0x1` にする — ため、reset を伴わない接続(`monitor`、`target info`、`read`、`dbg`)のあと、走っていた firmware は次の reset まで LinkE のクロックで走る。また **書込は RCC の周辺クロック enable と SysTick を 0 にして戻さず**、最後の reset で初めて元に戻る(`flash --reset none` では止まったまま)。ほかに: chip 消去は stub でなく LinkE 自身が行う(MER。`docs/cli.ja.md` の「stub の消去」は誤りだった)、ch32rv が送る stub はそのまま実行される(呼び出し規約も観測)、一括読み出しは abstract memory access + abstractauto で ABSTRACTCS を確かめない、attach 後に DATA0 に残る値は最後に読んだ ESIG の語(`0x1FFFF7F0`)、RedetectChip はクロックに触れないがその後の DMI は target に届かない、DmiOp 1 件は線上の DMI 1 frame ちょうど。

- (EN) Correction to 0.9.1: the note that "the probe's reset and run (`0x0b 0x01`) clears the Debug Module's pending halt request" generalised a CH549 WCH-Link (fw 2.12) + CH32V103 measurement to every probe. - (JA) 0.9.1 の訂正: 「probe の reset and run(`0x0b 0x01`)は DM の保留中 halt 要求を消す」という記述は、CH549 の WCH-Link(fw 2.12)+ CH32V103 での実測を probe 一般に広げたものだった。WCH-LinkE(fw 2.22)の線は逆で、`haltreq` を立ててから PFIC の system reset を出すので、hart は reset vector で止まって出てくる(0.8.0 の `reset` の修正が相手にしていたのもこれ)。0.9.1 より前の `run --exit-on semihosting` が CH549 のベンチでだけ落ちたのはこのため。0.9.1 の変更そのもの(`run` を `ndmreset` + `haltreq` 保持の DMI reset にしたこと)はどちらの probe でも正しく、コードのコメントの説明だけを狭めた。

## 0.10.0 - 2026-09-24

- (EN) New runtime source: `monitor --source dmseq` (also `run --source dmseq` and `arduino monitor`), the sequenced debug-module console - OEP `target.console` framing 2, specified in `oep-spec/docs/target-console-dmseq.ja.md` and agreed with the ArduinoCore-CH32 side after two review rounds. It carries the same DATA0/DATA1 mailbox as `dmdata`, but every word has a 1-bit sequence number in each direction and a CRC-8 (poly 0x07, init 0xFF) right after the payload, which is what lets a host tell a lost answer from a new frame: with `dmdata`'s framing a dropped answer makes the target's word be read twice (duplicated bytes, measured on a CH32L103) and reading it back to repair that cannot tell the duplicate from an identical next frame (a dropped byte, CH32V003). The CRC is not only for rare faults on this bench: an attach leaves `0xffffffff` in DATA0 and a CH32V30x flash leaves `0xe339e339`, whose bit 7 is clear, so without it a target takes that for a valid host answer. Target side: ArduinoCore-CH32's `SerialDMSeq` (`SerialDMDATA` and `SerialDMSeq` are exclusive - one framing per sketch). The host also reports two things the old source could not: `dmseq-target-timeout` when the target stopped waiting and dropped what it wrote in the meantime, and `dmseq-no-console` when nothing that parses as a frame arrives, instead of staying silent. Verified against the shipping `SerialDMSeq` on every family on the bench - CH32V003, CH32V006, CH32V103 (through the CH549 WCH-Link), CH32V203, CH32V307, CH32X035 and CH32L103: a known 1270-byte text came back byte-exact twice around an echo round trip on each, with the target reporting no reposts and no timeouts, including a target left latched for 12 s before the host attached; `run --source dmseq` streams it byte-exact as well, without a timeout warning, because `run` catches the target at its reset vector before opening the source. ArduinoCore-CH32's own smoke suite passed 14/14 on all seven boards with this build.
- (JA) 実行時 source を追加: `monitor --source dmseq`(`run --source dmseq` と `arduino monitor` も)。通番付きの debug module console で、OEP `target.console` framing 2(仕様 `oep-spec/docs/target-console-dmseq.ja.md`、ArduinoCore-CH32 側と 2 往復のレビューを経て合意)。搬送は `dmdata` と同じ DATA0/DATA1 mailbox だが、**全 word に両方向 1 bit の通番と CRC-8**(poly 0x07 / init 0xFF、payload 直後)が付く。これにより host は「落ちた答え」と「新しいフレーム」を区別できる — `dmdata` の framing では、答えが落ちると target の word を二度読んで**重複**し(CH32L103 で実測)、読み戻しで直そうとすると同内容の次フレームと取り違えて**欠落**する(CH32V003)。CRC は稀な故障のためだけではない: attach は DATA0 に `0xffffffff` を、CH32V30x の flash は `0xe339e339`(bit 7 が 0)を残すので、CRC が無いと target がそれを有効な答えとして受け取る。target 側は ArduinoCore-CH32 の `SerialDMSeq`(`SerialDMDATA` とは排他、sketch は一方のみ)。host は従来 source では出せなかった 2 つを報告する: target が答えを待つのをやめて出力を捨てた `dmseq-target-timeout` と、フレームとして解釈できる word が来ない `dmseq-no-console`(黙ったままにしない)。出荷版 `SerialDMSeq` に対し、**ベンチの全 family** — CH32V003 / CH32V006 / CH32V103(CH549 の WCH-Link 経由)/ CH32V203 / CH32V307 / CH32X035 / CH32L103 — で検証: 各機で既知の 1270 byte が echo 往復を挟んで 2 回とも byte 単位で一致(target 側の repost 0・timeout 0)。host が繋ぐ前に 12 秒放置して latch させた target でも同様。`run --source dmseq` でも byte 単位で一致し、timeout 警告は出ない(`run` は source を開く前に target を reset vector で止めるため)。ArduinoCore-CH32 側の smoke suite もこのビルドで 7 台すべて 14/14。

## 0.9.1 - 2026-09-23

- (EN) Fix: `run` erases before it programs, so the HIL runner works on a CH549 WCH-Link. The stub path is a full-region programmer that expects erased flash; `flash` erases first, but `run` went straight to `write_flash`. A WCH-LinkE tolerated that, so the runner worked on the rest of the bench, while on a CH549 Link (fw 2.12) + CH32V103 the probe simply never answered and every `run` that programmed died with `transfer timed out` at the image's first address - the same image flashing fine through `flash` a moment earlier. `run` always programs a whole image from the flash base, so it now does the chip erase that `flash --erase auto` would pick. Not a regression: a build from before this release's programming changes fails identically.
- (JA) 修正: `run` が書込前に消去するようになり、CH549 の WCH-Link でも HIL ランナーが動くようになった。stub 経路は消去済み flash を前提とする全 region 書込器で、`flash` は先に消すが `run` は `write_flash` へ直行していた。WCH-LinkE はこれを黙認するのでベンチの他機では動いていたが、CH549 Link(fw 2.12)+ CH32V103 では probe が応答を返さず、**書込を伴う `run` は必ず image 先頭で `transfer timed out`** になっていた(同じ image がその直前に `flash` では通る)。`run` は常に flash 先頭から image 全体を焼くので、`flash --erase auto` が選ぶ chip erase を行うようにした。**退行ではない**: この版の書込まわりの変更より前のビルドでも同じに落ちる。

- (EN) Fix: `run` catches the target at its reset vector instead of racing it. It reset through the probe's "reset and run" (`0x0b 0x01`) and halted afterwards, but that command clears the Debug Module's pending halt request, so the freshly programmed image starts immediately - and on a slow link the halt lands well inside it. Measured on a CH549 WCH-Link + CH32V103: `dpc = 0x2e`, some eleven instructions in, the program's first semihosting call already executed, so `--exit-on semihosting` waited out its cap for an exit it had missed (re-attaching does not help: the hart stays where the flash stub left it, `dpc = 0x200002ea` in SRAM). `run` now resets over DMI instead ([`DebugModule::reset_halt`]: `ndmreset` + `haltreq`, then release the reset with `haltreq` still asserted), which makes the hart enter debug mode out of reset before executing anything, and the semihosting CSR is armed while it sits there. Verified on all four benched families - CH32V103 (CH549 Link), CH32V203, CH32L103, CH32X035 - which now all exit 42 from `run tests/fixtures/semihosting.bin --exit-on semihosting`; the V103 never completed that run before.
- (JA) 修正: `run` が target を reset vector で捕まえるようになった(競争をやめた)。従来は probe の "reset and run"(`0x0b 0x01`)で reset してから halt していたが、このコマンドは **DM の保留中 halt 要求ごと流す**ので、焼いたばかりの image がすぐ走り出す。遅いリンクでは halt がその内側に落ちる — CH549 の WCH-Link + CH32V103 で実測: `dpc = 0x2e`(11 命令ほど進み、最初の semihosting 呼出を実行済み)。`--exit-on semihosting` は取り逃がした exit を cap いっぱい待っていた(再 attach も無効。hart は flash stub が残した `dpc = 0x200002ea` = SRAM に居座る)。`run` は DMI 経由の reset に変更した([`DebugModule::reset_halt`]: `ndmreset` + `haltreq` を立て、`haltreq` を保持したまま reset を解除)。hart は何も実行する前に debug mode へ入り、その間に semihosting 用 CSR を仕込む。**ベンチの 4 family すべてで確認** — CH32V103(CH549 Link)/ CH32V203 / CH32L103 / CH32X035 で `run tests/fixtures/semihosting.bin --exit-on semihosting` が exit 42(V103 はこれまで一度も完走しなかった)。

- (EN) The `run --exit-on semihosting` replay fixture is recorded on a CH32V203 again (`run-semihosting-v203.ndjson`). It had been re-recorded on a CH32V30x while the V203 board was off the bench.
- (JA) `run --exit-on semihosting` の replay fixture を再び CH32V203 で録音(`run-semihosting-v203.ndjson`)。V203 基板がベンチから外れていた間、CH32V30x で録り直していたもの。

- (EN) Fix: an ELF whose `.data` has initialised bytes now programs completely. A linker puts the `.data` initialiser at its own LMA directly behind `.text`, so the image arrives as two segments that meet mid-page (`LOAD 0x08000000 + 0x2bac`, then `LOAD` at `0x08002bac`, 16 bytes), and each segment was handed to the programmer on its own. The WCH-Link flash stub cannot start a write at a non-page-aligned address: it accepted the second write, acked it, and programmed nothing, so `flash` failed with `verify mismatch` at exactly the `.data` LMA - the last few bytes of the image, every time, on any image that has initialised globals. Measured on a CH32V307VCT6 + WCH-LinkE with an Arduino-built sketch: 11,196 B image, mismatch at `0x08002bac`, and a dump of that page showed the 16 initialiser bytes missing (`ff ff ff ff` where `fc 28 00 00 ...` belonged). Segments are now merged into whole programming units (`Image::program_blocks`) before programming - contiguous, overlapping, or same-unit segments become one block, padded with `0xff`, which cannot clear a cell and so programs identically. This also removes a latent double-program of one page on the FLASH-controller path (CH32V00x), where the same layout would have re-programmed an already written page. Verify still compares the image's own bytes, unpadded. The `flash-v307` replay fixture is re-recorded.
- (JA) 修正: `.data` に初期値を持つ ELF が最後まで書き込まれるようになった。linker は `.data` の初期値を `.text` 直後の LMA に置くので、image は **page の途中で接する 2 つの segment** として届き(`LOAD 0x08000000 + 0x2bac` の次に `LOAD 0x08002bac` の 16 byte)、それぞれ別々に programmer へ渡していた。WCH-Link の flash stub は **page 境界でない番地から書き始められない**: 2 本目の書込を受け取って ack を返しながら何も焼かないため、`flash` は `.data` の LMA ちょうど(= image の末尾数バイト)で毎回 `verify mismatch` になっていた。初期化済みグローバルを持つ image すべてが該当する。CH32V307VCT6 + WCH-LinkE + Arduino ビルドの sketch で実測: 11,196 byte の image が `0x08002bac` で mismatch、その page を dump すると初期値 16 byte が欠落(`fc 28 00 00 ...` のはずが `ff ff ff ff`)。segment は書込前に **programming unit 単位の block へ併合**するようにした(`Image::program_blocks`)— 連続・重複・同一 unit の segment を 1 つにまとめ、`0xff` で埋める(`0xff` はセルを落とせないので焼き上がりは同一)。FLASH-controller 経路(CH32V00x)で同じ配置が **同一 page を二度焼き**する潜在的な問題も、これで消える。verify は従来どおり image 自身のバイトだけを比較する。`flash-v307` の replay fixture は録り直した。

- (EN) Fix: an image made of more than one block now programs completely on the flash-stub path. The WCH-Link stub is a full-region programmer and **only the first `write_flash` of a session takes effect**: a second one is acknowledged like any other - the stub uploads, `Program 0x05/0x07/0x02` all reply normally, the data chunk is acked with `41 01 01 04` - and programs nothing, anywhere. Measured on a CH32V307VCT6 + WCH-LinkE with a two-block image (256 B at `0x08000000`, 88 B at `0x08004600`, both page-aligned, after a chip erase): the second block's page read back erased, and a dump showed the data had not landed at the first block's tail either. A detach/attach or a soft reset between the two writes does not help. `docs/protocol/wch-link.ja.md` §4.3 already recorded the same boundary from the other side (the stub path is for full-region programming after an erase). The stub path is now handed exactly one contiguous region per invocation (`Image::program_span`), gaps between blocks filled with `0xff`, which clears no cell. Because that region is what gets programmed, `--erase sector` now erases the pages of the region rather than of the raw segments - otherwise the filler would be programmed into unerased pages; `--restore-unwritten` puts the previous content of those pages back, as before. The FLASH-controller path (CH32V00x) drives whole pages itself and keeps taking the image's natural blocks. Reported from the ArduinoCore-CH32 bench as a deterministic `verify mismatch at 0x08004600` on an 18,008-byte sketch whose `.text` happened to end exactly on a page boundary, which is the case the segment merge in the entry above cannot cover (the segments touch, they do not share a unit).
- (JA) 修正: 複数 block からなる image が flash stub 経路で最後まで書き込まれるようになった。WCH-Link の stub は全 region 書込器で、**1 セッションで効くのは最初の `write_flash` だけ**。2 本目は他と同じように ack され(stub upload も `Program 0x05/0x07/0x02` も正常応答、data chunk も `41 01 01 04`)ながら**どこにも何も焼かない**。CH32V307VCT6 + WCH-LinkE で 2 block image(`0x08000000` に 256 B、`0x08004600` に 88 B、ともに page 整列、chip erase 済み)で実測: 2 つ目の page は消去状態のままで、dump しても 1 つ目の末尾に回り込んでもいなかった。間に detach/attach や soft reset を挟んでも変わらない。`docs/protocol/wch-link.ja.md` §4.3 が逆側から同じ境界を既に記録していた(stub 経路は消去後の全 region 書込用)。stub 経路には **1 回の実行につき連続 region を 1 つだけ**渡すようにした(`Image::program_span`。block 間の隙間は `0xff` 埋めで、セルは落ちない)。焼くのはその region なので、**`--erase sector` は生の segment ではなく region の page を消す**(そうしないと埋めを未消去 page に焼くことになる)。`--restore-unwritten` はこれまでどおりその page の元の内容を戻す。FLASH-controller 経路(CH32V00x)は page 単位で自分で駆動するので、従来どおり image 本来の block のまま。ArduinoCore-CH32 のベンチから、`.text` がちょうど page 境界で終わる 18,008 byte の sketch で決定的に `verify mismatch at 0x08004600` になると報告されたもの — 上の項の segment 併合では覆えないケース(segment は接しているだけで、同じ unit を共有していない)。

- (EN) Fix: `reset` (and `flash --reset run`) now leave the target actually executing. The probe's "reset and run" command (`0x0b 0x01`) puts the hart back at its reset vector, but when the probe still holds the halt request from attach - always the case for a standalone `reset`, which attaches and immediately resets - the hart re-enters Debug Mode on reset, and DetachChip only drops the request; a halted hart needs an explicit resume to leave. So `reset` printed `reset, running` while nothing ran. Measured on a CH32V006 with a UART heartbeat sketch: after `reset` the UART stayed silent for 5 s (3/3), and `reset --confirm-run=status` reported `running: false` (3/3); the next attach/detach cycle from any command then started it. `flash` was not affected because its verify step halts through the Debug Module, whose `halt` clears the request before the reset. Both paths now acknowledge the reset (DMCONTROL `ackhavereset`), read DMSTATUS, and issue a resume when the hart is halted. The acknowledge matters on the CH32V00x Debug Module: until the pending `havereset` is acknowledged its halt/running bits stay frozen at their reset-time values, so a running hart still read as halted (`0x004c0382`) and `--confirm-run=status` returned a false `running: false`; with the ack it reads `0x00430c82` (allrunning). After the fix the heartbeat appears 5/5 on the V006, `running: true` on both V006 and V307, and the `flash-v307` replay fixture is re-recorded to carry the extra exchange. Diagnosed by the ArduinoCore-CH32 side from the UART, after the first attempt here to verify it via `dbg reg read pc` was confounded by that command's own attach/resume - a target's running state has to be observed from outside the debug link.

- (EN) `--lock-timeout` now backs a real per-probe advisory lock (docs/cli.ja.md §3.7, ArduinoCore-CH32 request A-2): before a command touches a probe it takes an exclusive OS file lock keyed by the probe serial (or the bus topology when it has no serial), so two `ch32rv` processes on the same probe serialize instead of colliding - the bench can run a monitor and an upload against one probe without them stepping on each other.
