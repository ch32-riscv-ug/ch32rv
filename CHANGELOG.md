# Changelog

## Unreleased

- (EN) Fix `flash --erase sector`, which silently erased the *whole chip* (a data-loss footgun): `sector` was an unconditional alias for `chip`, so `flash small.bin --offset <high> --erase sector` wiped everything before writing 256 bytes. `sector` now erases only the flash pages the image actually covers, via the direct FLASH controller (`flash_page_erase`), then programs with the stub - so it never touches flash outside the image (a bootloader or calibration data in high flash survives). `chip`/`auto` still whole-chip-erase (the default flashing path is unchanged; note `--erase auto` with a partial image still erases the whole chip - use `sector` to preserve the rest). `sector` fails closed for families without a verified FLASH-controller profile. Segments sharing a page collapse so they cannot wipe each other. Added a pure `covered_pages` helper with unit tests (page-boundary, unaligned start, shared page, 128-byte page). Found and verified live on CH32L103: `flash <256B> --offset 0x0800FF00 --erase sector` leaves the firmware at 0x08000000 and the untouched middle region intact; also confirmed the stub programs correctly into page-erased (not chip-erased) flash.
- (JA) `flash --erase sector` が実は *chip 全体* を消していた data-loss footgun を修正: `sector` が無条件で `chip` の別名になっていて、`flash small.bin --offset <高位> --erase sector` が 256 byte を書く前に全 flash を消していた。`sector` は image が実際に覆う flash page だけを直接 FLASH controller(`flash_page_erase`)で消してから stub で program するようにし、image 外の flash(高位の bootloader・校正データ)を触らない。`chip`/`auto` は従来通り全 chip 消去(既定の書込経路は不変。ただし `--erase auto` で部分 image を焼くと今も全 chip を消す - 下位を残すなら `sector`)。検証済み FLASH-controller profile の無い family では fail-closed。同一 page を共有するセグメントは畳んで相互破壊を防ぐ。純関数 `covered_pages` を単体テスト付き(page 境界・非整列開始・共有 page・128byte page)で追加。CH32L103 で実機検証: `flash <256B> --offset 0x0800FF00 --erase sector` が 0x08000000 の firmware と未対象の中間域を無傷のまま対象 page だけ書換え。stub が page-erase 済み(chip-erase でない)flash へ正しく書けることも確認。

- (EN) Add CH32V103 to the direct FLASH-controller path, enabling `erase --range` on it. V103 differs from the other families in three ways found from the WCH EVT driver (ch32v10x_flash.c): a distinct fast-erase (128-byte page) vs program mechanism, a mandatory undocumented "commit" side effect after each op (`FLASH[0x4002_2034] = *((addr & ~3) ^ 0x1000)` - without it erase/program silently no-op), and reliable programming only via standard 16-bit halfword stores (CR_PG) rather than the fast buffer, so a new `write_mem16` (progbuf `sh`) and a `FlashProgMode::V103` were added (PG set once + one commit per page for speed, verified equivalent to the per-word EVT sequence). Verified live on CH32V103: `erase --range` erases a 128-byte page surgically (neighbours intact), and the flash program/erase round-trips correctly. gdb flash breakpoints also work on V103 once a V103-specific attach quirk is handled: the WCH-Link AttachChip overwrites the live GPR s1/x9 with the chip id (and saves the original nowhere), so a resumed program faults (load-address-misaligned, mcause=4) on its next use of s1. Root-caused from mcause/mepc/mtval and fixed by soft-resetting the target after attach so the program re-establishes its registers before we halt it; the profile flags this via `attach_corrupts_regs` and the gdb server restarts the target on those cores. Verified live on CH32V103: a plain `break` on flash-resident code fires across repeated `continue`.

- (EN) Add flash software breakpoints to the `gdb` server for cores without a hardware trigger module. A `break` GDB requests as software (Z0) now falls back, in order, to: a RAM `ebreak` patch, else a hardware execute trigger when free (no wear), else — new — an `ebreak` patched into flash by read-modify-writing the containing page via the direct FLASH controller. Code runs from the low alias (0x0000_0000) but the controller is given the physical flash address (0x0800_0000+off); reads mirror through either. Multiple breakpoints per page are handled, a set/clear that leaves the page unchanged skips the flash write, and every managed page is restored to pristine on detach (so an interrupted session never bakes an `ebreak` into flash). Verified live on the triggerless CH32V203: a plain `break` on flash-resident code fires across repeated `continue`, and after detach the page reads back its exact original instructions and the program runs. This costs flash wear (each set/clear rewrites a page; GDB's step-over rewrites twice), so the attach message warns and suggests `set breakpoint always-inserted on`. Covers the verified 256-byte-page families; V003 (64-byte buffered mode) and V103 are a follow-up.

Also handle RV32E cores (CH32V003, misa.E): only x0-x15 exist, so reading x16-x31 (which raises cmderr and previously killed the session) is skipped in both the gdb server and `dbg regs`. Attach never modifies flash. Verified live end to end with riscv-none-embed-gdb: RAM breakpoints stop `continue` on V003/V203; plain `break` on flash auto-uses a HW trigger and fires on V307/X035; a triggerless flash `break` is cleanly refused on V203.
