# CH32V407 の識別情報と保護解除の実測 (2026-10-10)

WCH-LinkE `49808F06CE30` に接続された実機をIDからCH32V407WEU6と識別した。
ユーザーの許可に基づいて読み出し保護を解除し、ユーザーFlashを全消去した。
解除前後のメモリ・設定・デバッグ情報を保存し、解除後のFlash全992 KiBを再読して一致を確認した。

## 識別情報

| 項目 | 実測 |
|---|---|
| Probe / firmware / port | WCH-LinkE / 2.22 (v42, raw `0216`) / `/dev/ttyACM20` |
| AttachChip family / ID / ChipInfo echo | `0xa6` / `0x46710011` / `0x46710011` |
| メモリ `0x1ffff704` | `11 00 71 46` (LE32 = `0x46710011`) |
| silicon revision / 比較用ID | 1 / `0x46710001` (`0xffffff0f` mask) |
| ChipInfo UID (8 byte) | `50ad1cd4c1ed546c` |
| UID領域 `0x1ffff7e8..0x1ffff7f3` (12 byte) | `d4 1c ad 50 6c 54 ed c1 39 e3 39 e3` |
| ChipInfo容量欄 / FLACAP `0x1ffff7e0` | `0x0240` / `40 02` (LE16 = 576 KiB) |
| ChipInfo protection_raw | `e339e339` |
| CSR misa / marchid / mimpid | `0x40b01107` / `0xdc68d876` / `0xdc688003` |

プローブUIDと12 byte UIDは異なる形式であり、末尾wordは消去パターン。
`protection_raw`から保護状態を判定せず、RDPRとFLASH_OBR.RDPRTを読む。

ローカルのWCH EVT `CH32V407/EVT/EXAM/SRC/Peripheral/src/ch32v4x7_dbgmcu.c`
V1.0.2 (2026-08-21) は、CH32V407WEUのIDを`0x467100x1`、
`DBGMCU_GetCHIPID`の番地を`0x1ffff704`と定義する。実測はこれと生成DBのWEU6行に一致。
パッケージ刻印の目視確認はしていない。

## 保護解除と消去

| 項目 | 解除前 | 解除後 |
|---|---|---|
| Option raw (16 byte) | `ff00bf40ff00ff00ff00ff00ff00ff00` | `a55abf40ff00ff00ff00ff00ff00ff00` |
| RDPR / 読み出し保護 | `0xff` / 有効 | `0xa5` / 無効 |
| FLASH_OBR (`0x4002201c`) | `0x03fffefe` | `0x03fffefc` |
| USER / WRP | `0xbf` / `0xffffffff` | 保持 |

`target protect off --yes`は実機で成功し、Option readbackを検証した。
RDPRと補数の2 byte以外は不変。解除後の読み出し・書き込み保護は無効。
解除はユーザーFlashのmass eraseを伴う。新しいアプリは書き込んでいない。

解除前のFlash全領域とBOOTは`0xe339e339`を返したが、これは保護下の読取値。
**解除前dumpは元firmwareのバックアップではない。元firmwareは保護解除に伴って消去済み。**

## 取得範囲と検証

| 領域 | 範囲・取得量 | 確認 |
|---|---|---|
| ユーザーFlash全体 | `0x08000000..0x080f7fff`、992 KiB、解除前後 | 解除後は全word `0xe339e339`。別セッション・high speedの再読とbyte一致 |
| BOOT | `0x1fff8000..0x1fffefff`、28 KiB、解除前後 | 解除後はコードを取得。System window内の別読取と一致 |
| System window | `0x1fff0000..0x1fffffff`、64 KiB | BOOT、SFDP、電子署名、工場設定、128 byte Option領域を含むraw |
| SRAM | `0x20000000..0x20031fff`、200 KiB、解除前後 | raw snapshot。実際の分割容量は未確定 |
| CPU / Debug Module | GPR x0..x31とPCを解除前後、CSR 76アドレス、DMI 20アドレス | 読取値・通信captureを保存 |
| 周辺レジスタ | RMのアドレス表由来61ブロック、1036エントリ | rawとアドレス・値の対応表を保存 |

Flash全体SHA-256: `4d5d88b15942db8817f4e6caf46771c84549e10fe0722c7f6299071aebddf5ba`。
解除後BOOT SHA-256: `edc460a956eaa303d28dd468ad7f034cb95b7b5eeae54b5585984c3404721b08`。

ローカルのWCH `CH32V407RM.PDF` 英語V1.2、§32.1のFlash範囲は992 KiB。
`CH32V407DS0.PDF` 英語V1.2、§1.4.2は通常の分割をFlash 512 + 480 KiB / SRAM 200 KiB、
変更時をFlash 576 + 416 KiB / SRAM 136 KiBと記載する。
プローブ・FLACAPは576 KiBを返すが、生成DBはゼロウェイト512 KiB / SRAM200 KiB。
**576 KiBと200 KiBを同時に検証済みの容量として扱わない。** SRAM分割は別途検証が必要。
総Flash読取でCLIが576 KiB以降に範囲警告を出すのは、DBのメモリマップが総量を扱わないため。

RAM・レジスタは順次読取であり、単一時点のCPU状態を復元するバックアップではない。
CSR読取の成功や0値だけで、各アドレスの実装有無を断定しない。
未接続の外部ストレージと未定義アドレス空間は探索していない。
attach時に間欠的な`target-no-response`があり、成功した再試行も記録した。

## 登録状態と検証の境界

WEU6のIDは生成DBに収載済み。この実測ではDBの`verified`やfamily tableを変更していない。
現CLIではfamily byte `0xa6`が未登録のため`unknown(0xa6)`警告が出る。
SKUはIDから一意に識別でき、DB family `CH32V407`に基づくOption操作は成功した。
capabilities上のFlash書き込み・部分消去は未対応のまま。
V205/X315で実施したloader、Flash breakpoint、semihosting、通信fixture等の実機試験は、
今回のデータ取得・保護解除とは別の未実施項目。
