# CH32H417 の識別情報とデータ取得実測 (2026-10-10)

M030からH417へ入れ替えたWCH-LinkE `49808F06CE30` のSWIO経由で、CH32H417QEU6を識別した。
読み出し・書き込み保護は無効。既存FlashとOptionを保持し、書き込み・消去なしで取得した。
Flash全960 KiBとBOOT56 KiBの別読取がbyte一致した。

## 識別と電子署名

| 項目 | 実測 |
|---|---|
| Probe / firmware / port | WCH-LinkE / 2.22 (v42, raw `0216`) / `/dev/ttyACM20` |
| AttachChip family / ID / ChipInfo echo | `0xc6` (`CH32H4`) / `0x4170053d` / `0x4170053d` |
| メモリ `0x1ffff704` | `3d 05 70 41` (LE32 = `0x4170053d`) |
| silicon revision / 比較用ID | 3 / `0x4170050d` (`0xffffff0f` mask) |
| ChipInfo UID (8 byte) | `640eb63cb6c99c7f` |
| UID `0x1ffff7e8..0x1ffff7f3` (12 byte) | `3c b6 0e 64 7f 9c c9 b6 39 e3 39 e3` |
| FLACAP `0x1ffff7e0` / ChipInfo容量 | `c0 03` (LE16 = `0x03c0`)、960 KiB |
| ChipInfo protection_raw | `e339e339` |
| Option base / raw (先頭16 byte) | `0x1ffff800` / `a55aff00ff00ff00ff00ff00ff00ff00` |
| RDPR / USER / WRP | `0xa5` / `0xff` / `0xffffffff`、取得前後で不変 |
| FLASH_CFGR0 / DBMODE | `0x96070200` / 1 (double Flash mode) |
| 既定コア misa / marchid / mimpid / mhartid | `0x40901127` / `0xdc68d866` / `0xdc688002` / 0 |

ローカルWCH EVT `CH32H417/EVT/EXAM/SRC/Peripheral/src/ch32h417_dbgmcu.c` の
`DBGMCU_GetCHIPID`はQEUのIDを`0x417005xD`、番地を`0x1ffff704`と定義する。
実測はrevisionを除いて生成DBと一致。型番はIDによる識別で、刻印の目視確認はしていない。
SWIOはPB9、2-wire時のクロックはPB8。UIDのプローブ8 byteと領域12 byteは別形式で、
末尾wordは消去パターン。`protection_raw`から保護状態を推定せず、Optionを読む。

## 取得範囲と検証

ローカルWCH `CH32H417RM.PDF` 英語V1.8、§1.2.1と§46.1は、
DBMODE=1のFlash960 KiB / BOOT56 KiBと、RAM3領域の総896 KiBを定義する。
電子署名番地は§39.2に記載。実測容量・DBMODE・SKU容量は一致する。

| 領域 | 範囲・量 | 結果 |
|---|---|---|
| Flash | `0x08000000..0x080effff`、960 KiB | 既存プログラムを取得。別セッションの再読とbyte一致 |
| BOOT | `0x1fff0000..0x1fffdfff`、56 KiB | コードを取得。System window内の別読取と一致 |
| System window | `0x1fff0000..0x1fffffff`、64 KiB | BOOT、工場設定、電子署名、Option256 byteのraw |
| ITCM | `0x200a0000..0x200bffff`、128 KiB | raw snapshot |
| DTCM | `0x200c0000..0x200fffff`、256 KiB | raw snapshot |
| Shared RAM | `0x20100000..0x2017ffff`、512 KiB | raw snapshot |
| PIOC RAM / IPC shared RAM | `0x50040000+4096` / `0x40006000+512` | raw snapshot |
| 既定コア / Debug Module | GPR x0..x31、PC、FPR f0..f31、CSR50アドレス、DMI14アドレス | 読取値と通信capture |
| 周辺レジスタ | RMアドレス表由来85ブロック、1758エントリ | rawとアドレス・値の対応表 |

Flash SHA-256: `74845313d09a0521f674fc3cbe71929a66b567fbb1904ec258538212c95d9e97`。
BOOT SHA-256: `c57825e13b9047481f5f3d511b02fca0f9186cf612de2cd41e237b5ca8823192`。
RAM番地はRMに基づく。CLIのH417 RAMマップが未整備で、範囲警告は原本に残す。

FPRはDebug Moduleのabstract register番号`0x1020..0x103f`で読み出した。
現CLIの`dbg reg read csr:<number>`は番号をabstract commandへ渡すため、この経路を使用した。
これらの番号はRISC-VのCSR番地ではない。

**第2コアのレジスタは未取得。** 現CLIの`--core 1`は`capability-unsupported` (exit24)で拒否する。
既定コアの`mhartid=0`を確認した。両コアの状態を取得済みとは扱わない。
RAM・レジスタは順次読取であり、単一時点の状態復元用ではない。周辺のデータレジスタ読取は
周辺状態を消費する場合がある。CSR/DMI読取の成功や0値だけで実装有無を断定しない。
未接続の外部メモリと未定義アドレス空間は探索していない。

実機取得はch32rv 0.19.0 / Linux x86_64、DB源泉ch32-device-data@773f929。
詳細は原本の`version-0.json`と実行ログ。
初期attachは応答なしだったが、再確認後はlow / mediumで識別が成功した。
失敗・成功の両captureを原本に保持する。原因は確定していない。

IDとfamilyは既存DB・CLIに登録済み。今回DBの`verified`は変更していない。
Flash書き込み・消去・loader・第2コア選択・通信fixture等の機能試験は未実施。
