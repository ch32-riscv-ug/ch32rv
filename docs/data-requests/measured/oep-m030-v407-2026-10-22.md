# CH32M030 / CH32V407 を OEP の probe で検証 (2026-10-22)

ユーザーが OEP の probe 2 台に、ともに 1 線 / 2 線の両方に対応する CH32M030 と CH32V407 をつないだ。ch32rv の書き込みとデバッグを、2 チップで初めて実機で通した。

## 構成

| target | probe(firmware) | 配線 | ラベル(core `channel.{}.label`、save 済み) |
|---|---|---|---|
| CH32M030G8R7(chip id `0x03BB0810`) | ESP32-P4X `e8f60ae84e28`(0.0.36+f8ac55a → 12e1222) | GPIO31 = SWIO(PA3)、GPIO30 = USART1 TX(PB6) | `m030.swio`、`m030.rx` |
| CH32V407WEU6(chip id `0x46710011`) | ESP32-P4 `30eda0ea068b`(同上) | GPIO31 = SWDIO(PA13)、GPIO30 = SWCLK(PA14) | `v407.swio` |

どちらも chip id は DB の値と、リビジョンの bit [7:4] だけが違う。

## 1 線でしか答えない

V407 のデータシート(§1.4.32)は「1 線が既定、2 線は SWDIO と SWCLK」。電源を入れ直した直後でも、GPIO28〜33 のどの組でも、SWCLK を high / low のどちらで休ませても、RVSWD は答えなかった。1 線(SWIO)は GPIO31 で答える。LinkE は接続時に 2 線へ切り替えているとみられるが、手順は分かっていない(wch-protocols の未解決事項)。以下はすべて 1 線(`oep.wire.swio`)で通した。

1 線で読んだ WCH の DMI 番地(attach の直後、ch32rv も LinkE も書く前):

| | 0x7C | 0x7D | 0x7E | 0x7F |
|---|---|---|---|---|
| V407 | `0x11538403` | `0x5AA58401` | `0x00000400` | `0x46710011` |
| M030 | `0x11038403` | `0x5AA58401` | `0x00000400` | `0x03BB0810` |
| 参考: V003(1 線のみ、LinkE の接続後) | `0x00010403` | `0x5AA50401` | — | — |

### 2 線への切り替えの実験(V407)

QingKe V3 / V5 の中国語版マニュアル 7.1 節に、この 3 つの番地の表がある: 0x7C `capabi`(RO: [31:28] 1 線の版、[27:24] 2 線の版、[23:18] 1 線のサンプリング周波数、[17:16] `dmi_info` = 3 で 1/2 線の両方、bit 15 両対応、bit 10 出力可)、0x7D `config`(bit 15 `swdmd`: 表では 1 = 2 線 / 0 = 1 線、既定 1。bit 10 `outen`。[1:0] `psc1x` 1 線の速さ)、0x7E `config_pre`(同じ並びの予約値)。書くときは `config_pre` に鍵 `0x5AA5` を付けて書き、続けて(他のレジスタを挟まずに)`config` に鍵と、反映させるビットのマスクを書く。V2 / V4 の英語版マニュアルは「WCH Debug Protocol Manual」を参照するが、その文書は公開されていない。

- 1 線で読んだ `config` は `swdmd` = 1。`config_pre` = `0x5AA58401` → `config` = `0x5AA58000`(同じ値を書き直す)は受け付けられ、何も変わらなかった。
- `config_pre` = `0x5AA50401`(`swdmd_pre` = 0)→ `config` = `0x5AA58000` を書いた直後に 1 線の通信が切れた。このビットで線の方式は実際に切り替わる(実機では表と意味が逆に見える)。
- その後、OEP の `oep.wire.rvswd` は GPIO30/31 のどの組でも、SWCLK の休ませ方 high / low、1 MHz / 200 kHz / 50 kHz のどれでも答えず、1 線にも戻らなかった。電源の入れ直しが要る。
- LinkE は接続の最初に long 形式の DMSTATUS の問い合わせを 202 回送る(wch-protocols link-to-target §5)。1/2 線のチップの 2 線がその形式を要るのかは未確認。手順を確かめるには、LinkE と V407 の線を収録する必要がある。

M030 は SWCLK(PA2)をつないでいないので、2 線は試していない。

## 見つけた不具合

- **probe の run が haltreq を立てたまま返す**(oep-probe-arduino 0.0.36+f8ac55a): ebreak で止まった後、DMCONTROL が `0x80000001` のまま。M030 / V407 の DM は haltreq が立っている間の resumereq を無視するので、同じ接続の 2 回目以降の run と resume が 1 命令も進まない。ch32rv のローダーは 1 回目の run の分(V407 は 4 KiB、M030 は 1 KiB)しか書けず、`read` の後に hart が止まったままになった。X035 / L103 では起きない。probe は 12e1222 で直った。ch32rv も run と resume の前に haltreq を下ろす(7ef34ab)。
- **fixture UART は RX だけでよい**: ch32rv は `rx` と `tx` の両方のラベルを求めていたが、oep-if-fixture §2 の UART は RX だけの plan を許す(受信だけ)。M030 は TX しかつないでいないので、rx だけで開くようにした(bd38142)。
- **OEP の `flash --preverify` が無視されていた**: 実装した(e1124d4)。
- **ArduinoCore の M030 の 72 / 48 / 24 MHz**: SystemInit で mcause 2(mepc `0xE00009A0`)。PLL は固定の 144 MHz で HPRE /2 が要るのを生成器が読んでいなかった。ArduinoCore-CH32RV e3ebb34 で直り、3 つとも起動と UART の出力を確かめた。

## 通ったコマンド(12e1222、ch32rv main)

両チップとも exit 0: `target info`、`capabilities`、`flash`(`--verify readback` / `crc`、`--preverify`、`--confirm-run pc`)、`verify`、`read`(code、RAM、option)、`target option get`、`erase --range`(V407 は 4 KiB を 1 ページ、M030 は 32 ページ)、`reset`(`--halt` で pc 0、`--confirm-run status` / `pc`)、`dbg halt` / `step` / `regs` / `reg read` / `resume`。`monitor --source fixture-uart`(M030、115200 bps)。

- 書き込み: V407 17,456 B(5 ページ、約 2.0 s)、M030 6,104 B(48 ページ × 128 B、約 1.1 s)。
- V407 のスケッチは flash の 16 KiB のパターンの和を RAM に置き(`0x28040400`、期待値と一致)、RAM のカウンタは `read` のたびに進んだ。
